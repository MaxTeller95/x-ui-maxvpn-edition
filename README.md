# xui-optimizer

ابزارها و صفحه‌ی **Optimizer** برای هابی که پنل [x-ui / 3x-ui](https://github.com/MHSanaei/3x-ui) رویش است
و ترافیک کاربران را از راه تانل به سرورهای خارج می‌فرستد (معمولاً سرور داخل ایران ← سرور خارج).
همه‌ی عددهای این راهنما روی یک هاب واقعی با حدود ۱۴۰ کاربر و دو سرور خارج اندازه گرفته شده‌اند.

هر ابزار:
- مستقیم دیتابیس خود پنل را ویرایش می‌کند، پس پنل تغییرات را نگه می‌دارد و در **Xray Configs** نشانشان می‌دهد؛
- کانفیگ جدید را **قبل از** هر تغییری با `xray run -test` می‌سنجد؛
- از دیتابیس پنل (`x-ui.db`، یا برای PostgreSQL یک `x-ui.pgdump`) و `config.json` در `/root/xui-backup-<زمان>/` بکاپ می‌گیرد؛
- با اجرای دوباره، قانون‌های خودش را جایگزین می‌کند، نه اینکه دوباره اضافه کند.

## حساب ترافیک کاربران، بایت به بایت

3x-ui ترافیک هر کاربر را از شمارنده‌های Xray حساب می‌کند: هر ۵ ثانیه آن‌ها را می‌خواند و اختلاف را به حساب کاربر
می‌نویسد. با هر **ری‌استارت Xray** دو تکه از دست می‌رود و هرگز حساب نمی‌شود: آنچه پروسه‌ی قبلی از آخرین خواندن شمرده بود،
و آنچه پروسه‌ی جدید تا اولین خواندن می‌شمارد (پنل بعد از ری‌استارت فقط نقطه‌ی شروع برمی‌دارد). یعنی تا حدود ۱۰ ثانیه از
ترافیک همه‌ی کاربران، به‌علاوه‌ی قطع شدن همه‌ی اتصال‌ها.

برای همین هیچ ابزاری در این پروژه برای کاری که Xray زنده قبول می‌کند ری‌استارت نمی‌کند (`lib/xuilive.py`):

- اوت‌باندها و پورت‌های probe تک‌تک از راه API عوض می‌شوند؛ همه‌ی قانون‌ها و بالانسرها با یک فراخوانی، یکجا
- قانون‌هایی که خود پنل به کانفیگ اضافه می‌کند (مثل `panel-egress`) و حذف `enabled`/`comment` دقیقاً مثل پنل حساب می‌شوند
- فقط چیزی که Xray زنده نمی‌پذیرد (بخش dns، observatory، فهرست‌های geo، اینباندهای کاربران) ری‌استارت می‌خواهد، و آن وقت
  فقط Xray از نو ساخته می‌شود (`systemctl reload x-ui`)، نه کل پنل

آزمایش روی هاب: دو تغییر واقعی ترکیب تانل در ۴۰ ثانیه، پروسه‌ی Xray همان ماند، Xray ۲۲.۴ مگابایت شمرد و پنل ۲۲.۳ مگابایت
حساب کرد (اختلاف فقط زمان‌بندی خواندن ۵ ثانیه‌ای پنل است). ترکیب تانل‌ها هم ترافیک هیچ کاربری را دو بار حساب نمی‌کند.

**توصیه:** در تنظیمات Xray پنل، «ری‌استارت Xray هنگام غیرفعال شدن کاربر» (`restartXrayOnClientDisable`) را خاموش کنید.
روشن باشد، هر بار که کاربری منقضی یا حجمش تمام شود، پنل کل Xray را ری‌استارت می‌کند (همه‌ی کاربران قطع و همان چند ثانیه‌ی
حساب‌نشده). خاموش باشد، فقط همان کاربر از راه API برداشته می‌شود و اتصال‌های باز او هم همچنان به حساب خودش نوشته می‌شود.

## دیتابیس پنل: SQLite یا PostgreSQL

3x-ui نسخه‌ی 3 می‌تواند اطلاعاتش را به‌جای `/etc/x-ui/x-ui.db` در PostgreSQL نگه دارد (`XUI_DB_TYPE=postgres` و
`XUI_DB_DSN` در `/etc/default/x-ui`). همه‌ی ابزارها از یک ماژول مشترک (`lib/xuidb.py`) استفاده می‌کنند که دیتابیس را
همان‌طور که خود x-ui می‌بیند پیدا می‌کند: محیط پروسه‌ی x-ui در حال اجرا، بعد تنظیمات سرویس، بعد SQLite پیش‌فرض.

- برای PostgreSQL از `psql` و `pg_dump` استفاده می‌شود (نصب‌کننده اگر نباشند نصبشان می‌کند) و رمز روی خط فرمان نمی‌آید.
- تغییرها مثل SQLite همه با هم و در یک تراکنش نوشته می‌شوند.
- بکاپ‌ها برای PostgreSQL یک `pg_dump` کامل‌اند و برگرداندن هم از صفحه‌ی Optimizer و هم با این دستور است:

```bash
xui-db detect                                  # کدام دیتابیس پیدا شده
xui-db backup /root/my-backup                  # بکاپ دستی
xui-db restore /root/xui-backup-<زمان>/x-ui.pgdump   # برگرداندن (x-ui را متوقف و دوباره روشن می‌کند)
```

ابزارهای ارتقای 2.x به 3.x (`migrate/upgrade-2x-to-3x.sh`) فقط SQLite هستند، چون پنل 2.x PostgreSQL ندارد.

## نصب

**با git clone:**

```bash
git clone https://github.com/MaxTeller95/xui-optimizer.git
cd xui-optimizer && sudo bash install.sh
```

صفحه‌ی Optimizer به‌صورت پیش‌فرض نصب می‌شود، یکپارچه روی **پورت اصلی پنل** (nginx پورت پنل را می‌گیرد و x-ui به
127.0.0.1 می‌رود). اگر پنل گواهی TLS نداشته باشد، صفحه رد می‌شود و ابزارها نصب می‌مانند. فقط ابزارها یا آزمایشی:

```bash
sudo bash install.sh --no-dash       # بدون صفحه
sudo bash install.sh --dash 59085    # آزمایشی روی پورت دوم؛ پنل روی پورت خودش هم می‌ماند
```

**با یک دستور** (ریپو خصوصی است؛ توکن GitHub با دسترسی خواندن لازم است و روی سرور ذخیره نمی‌شود):

```bash
export GITHUB_TOKEN=<token>
bash <(curl -fsSL -H "Authorization: token $GITHUB_TOKEN" https://raw.githubusercontent.com/MaxTeller95/xui-optimizer/main/install.sh)
```

| گزینه | کار |
|---|---|
| *(بدون گزینه)* | ابزارها + صفحه‌ی Optimizer یکپارچه روی پورت اصلی پنل |
| `--no-dash` | فقط ابزارها؛ صفحه‌ی Optimizer نصب نشود |
| `--dash PORT` | صفحه‌ی Optimizer روی پورت دیگر (آزمایشی، پنل روی پورت خودش هم می‌ماند) |
| `--move` | همراه `--dash <پورت پنل>`: همان حالت پیش‌فرض |
| `--uninstall` | ابزارها، سرویس‌ها و صفحه را حذف می‌کند؛ تنظیمات و بکاپ‌ها می‌مانند |

- سورس در `/opt/xui-optimizer` و ابزارها در `/usr/local/sbin` نصب می‌شوند.
- پیش‌نیازها (`git`، `python3`، `curl`، `sqlite3` و برای صفحه `nginx`) اگر نباشند خودکار نصب می‌شوند.
- **به‌روزرسانی:** همین اسکریپت را دوباره اجرا کنید. آخرین نسخه را می‌گیرد، تایمرهای روشن را با نسخه‌ی جدید ادامه می‌دهد
  و اگر صفحه‌ی Optimizer نصب باشد آن را هم به‌روز می‌کند، بدون دست زدن به تنظیمات پنل.
- **نصب به تنهایی چیزی را در پنل عوض نمی‌کند.** هیچ تایمری روشن نمی‌شود.

### ترتیب پیشنهادی روی یک هاب تازه

```bash
xui-optimizer --dry-run && xui-optimizer          # کش DNS و بستن تبلیغات
xui-split && xui-split apply                      # تقسیم ترافیک، پورت‌های probe برای نگهبان
cp sysctl/99-proxy-tcp.conf /etc/sysctl.d/ && sysctl -p /etc/sysctl.d/99-proxy-tcp.conf
nano /etc/tunnel-guard.json && tunnel-guard --check && tunnel-guard --test
systemctl enable --now tunnel-guard.timer
config-guard && systemctl enable --now config-guard.path config-guard.timer
systemctl enable --now xui-tunnel.timer
```

روی هر سرور خارج: `abroad-tune && abroad-tune apply` و همان فایل sysctl.

## xui-optimizer - بستن تبلیغات و کش DNS

- **بستن تبلیغات:** `geosite:category-ads-all` برای هر اینباندی که به پروکسی می‌رود به blackhole می‌رود؛
  تبلیغ و ردیاب اصلاً از تانل رد نمی‌شوند.
- **کش DNS:** DNS کاربران (پورت ۵۳) روی خود هاب جواب داده می‌شود. فقط وقتی در کش نباشد، به‌صورت DoH به
  1.1.1.1 / 8.8.8.8 **از داخل تانل** پرسیده می‌شود، نه از DNS داخلی. حدود ۱۰۰ میلی‌ثانیه بار اول، ۰٫۱ میلی‌ثانیه بعد از آن.
- **Sniffing با routeOnly** تا بستن تبلیغات برای کلاینتی که IP خام می‌فرستد هم کار کند.

```bash
xui-optimizer --dry-run   # بساز و تست کن، چیزی عوض نکن
xui-optimizer             # بکاپ، تست، اعمال، ری‌استارت x-ui
xui-optimizer --remove    # برگرداندن
xui-optimizer --adblock on|off     # فقط بستن تبلیغات؛ قانون‌های دیگر دست نمی‌خورند
xui-optimizer --quic block|allow   # فقط بستن QUIC (UDP 443) برای کاربران
```

**بستن QUIC.** یوتیوب، اینستاگرام و مرورگرها اول QUIC (HTTP/3 روی UDP 443) را امتحان می‌کنند. داخل تانل TCP، این
UDP با دو کنترل ازدحام روی هم حمل می‌شود و اولین چیزی است که در مسیر محدود می‌شود. وقتی رد شود، اپ در کمتر از
یک ثانیه با HTTPS روی TCP دوباره وصل می‌شود که داخل تانل معمولاً سریع‌تر و پایدارتر است. روی یک هاب واقعی
حدود ۱۴٪ اتصال‌های کاربران QUIC بود؛ بعد از روشن کردن، همه‌ی تلاش‌های QUIC رد و همان اپ‌ها روی TCP وصل شدند.
صفحه‌ی Optimizer سهم QUIC و تعداد برگردانده‌شده‌ها را از لاگ دسترسی نشان می‌دهد.

`--dns-via OUTBOUND` مسیر DoH را انتخاب می‌کند؛ `--no-adblock` و `--no-dns` یک بخش را کنار می‌گذارند.
قانون‌های خودتان که باید اول اعمال شوند (مثلاً سایت‌های ایرانی مستقیم) باید **بالاتر** از قانون کش DNS باشند.

### DNS سریع

اندازه‌گیری روی هاب: جوابی که در کش نیست (DoH از راه تانل) میانه‌ی **۹۴ و تا ۳۷۹ میلی‌ثانیه** طول می‌کشد و جواب از کش
**۰.۱ میلی‌ثانیه**. دامنه‌های پرکاربرد (اینستاگرام، یوتیوب، CDNها) مهلت (TTL) یک تا پنج دقیقه‌ای دارند، پس کاربر مرتب
هزینه‌ی همان کش‌نشدن را می‌دهد. در حالت سریع:

- جواب منقضی‌شده تا یک ساعت فوری داده می‌شود و Xray پشت صحنه تازه‌اش می‌کند (`serveStale`، `serveExpiredTTL: 3600`)
- هر دو سرور DoH همزمان پرسیده می‌شوند و جواب سریع‌تر برداشته می‌شود (`enableParallelQuery`)

```bash
xui-optimizer --dns on           # یا off؛ فقط کش DNS، بقیه‌ی قانون‌ها (تبلیغات، QUIC، امنیت) دست نمی‌خورند
xui-optimizer --dns-fast on      # یا off؛ فقط بخش dns عوض می‌شود، با بکاپ و یک ری‌استارت
```

نصب تازه‌ی کش DNS از اول در حالت سریع است. هر دو سرور خارج IPv6 دارند، پس جواب‌های IPv6 هم داده می‌شوند.

## xui-split - mux فقط جایی که فایده دارد

mux دست‌دادن TCP روی تانل را حذف می‌کند (صفحه‌ها ~۱۹٪ سریع‌تر باز می‌شوند) ولی سقف دانلود جمعی را پایین می‌آورد
(۸۱۵ ← ۴۸۰ مگابیت). پس:

- **سبک** (صفحه‌ها، پیام‌رسان‌ها، APIها) ← `<MAIN>-mux`
- **سنگین** (ویدیو، CDN اینستاگرام، آپدیت‌ها، دانلودها، تست سرعت)، **UDP** و **تلگرام** ← `<MAIN>`

**هر خروجی جدا.** هاب ممکن است کاربران را به چند سرور در چند کشور بفرستد (مثلاً `MAIN` در یک کشور و `BACKUP`
در کشور دیگر). هر اوت‌باندی که یک قانون کاربران را به آن می‌فرستد یک «گروه» است و همه‌چیزش جداست:

| برای هر خروجی | نام |
|---|---|
| اوت‌باند mux | `<OUT>-mux` |
| قانون‌ها | `split-<out>-udp`، `split-<out>-heavy`، `split-<out>-telegram` ← `<OUT>` و `split-<out>-light` ← `<OUT>-mux` |
| قانون اصلی | `main-<out>` |
| پورت probe | `guard-<out>-mux` |
| تنظیمات | در `/etc/xui-split.json`: روشن/خاموش، concurrency، xudp، برچسب (مثلاً «کشور یک») و دامنه‌های سنگین اضافه |

مسیرهای دیگر به همان سرور (تانل دوم، مسیر sing-box، مسیر Reality) گروه جدا نیستند. نگهبان تانل هر mux را جدا
می‌سنجد: اگر mux یک خروجی گیر کند فقط ترافیک سبک همان خروجی از mux برداشته می‌شود.

```bash
xui-split          # تست (پیش‌فرض)
xui-split apply    # اعمال؛ بکاپ روزانه‌ی تلگرام پنل را هم روشن می‌کند
xui-split remove
xui-split groups                                   # خروجی‌ها، اینباندها و تنظیمات هر کدام
xui-split set BACKUP --label "کشور دو" --concurrency 8  # تنظیم یک خروجی؛ بعد fix (فقط mux) یا apply (روشن/خاموش)
mux-bench <OUTBOUND>   # قبل از اعمال، روی لینک خودتان بسنجید
```

`xui-split check` می‌سنجد تقسیم واقعاً کار می‌کند یا نه: اوت‌باند `<MAIN>-mux` هست، mux رویش روشن است، با
اوت‌باند اصلی یکی است (آدرس، مسیر sing-box، مشخصات)، قانون‌های split به ترتیب درست‌اند، پورت probe هست، و
Xray در حال اجرا هم mux را دارد. `xui-split fix` هر چه خراب باشد تعمیر می‌کند: اگر فقط اوت‌باند mux خراب باشد
از راه API و **بدون ری‌استارت**، وگرنه با ساخت دوباره و ری‌استارت. ویرایشگر خود پنل ممکن است اوت‌باند mux را بدون
بخش mux ذخیره کند؛ config-guard بعد از هر بار نوشته شدن کانفیگ این را می‌بیند و بدون ری‌استارت درستش می‌کند.
در صفحه، زیر کلید تقسیم ترافیک وضعیت واقعی mux و دکمه‌ی «تعمیر خودکار» هست.

### mux هوشمند

اینکه چند اتصال روی یک اتصال mux بروند (concurrency) عدد ثابتی نیست: بیشتر یعنی دست‌دادن کمتر از روی تانل (هر کدام یک
رفت‌وبرگشت ۸۰ تا ۱۰۰ میلی‌ثانیه‌ای)، ولی با پکت لاست یک بسته‌ی گم‌شده همه‌ی اتصال‌های روی آن را نگه می‌دارد. پس اندازه
گرفته می‌شود، نه حدس زده:

- هر ۳۰ دقیقه (`xui-split-tune.timer`) برای هر خروجی، روی همان اوت‌باند mux خودش (برای مسیر ترکیبی روی تانلی که در ترکیب
  و سالم است) در یک Xray موقت، concurrency‌های ۲، ۴، ۸، ۱۶ و مقدار فعلی امتحان می‌شوند: هر دور ۱۶ درخواست کوچک HTTPS
  همزمان، مثل باز شدن یک صفحه، چند دور به ترتیب تصادفی بعد از یک دور گرم‌کردن. کاربران دست نمی‌خورند.
- تنظیم‌هایی که تا ۵٪ با بهترین فاصله دارند برابر حساب می‌شوند؛ آن وقت مقدار فعلی، وگرنه کمترین، انتخاب می‌شود.
- اگر تانل ۲٪ یا بیشتر پکت لاست داشته باشد، بالاتر از ۴ انتخاب نمی‌شود.
- فقط برای ۲۵٪ بهتر شدن، یا ۱۰٪ که دو بار پشت سر هم تکرار شود، عوض می‌شود؛ بی ری‌استارت از راه API (کپی‌های مسیر ترکیبی
  هم، بدون برگرداندن تانلی که برای لاست بیرون است) و با پیام تلگرام.
- در صفحه: «خودکار» یا یک عدد که 🔒 قفل دستی است و خودکار به آن دست نمی‌زند؛ ⟳ همین حالا اندازه می‌گیرد.

```bash
xui-split tune                 # فقط اندازه‌گیری و نتیجه
xui-split tune MAIN --apply # اندازه‌گیری و اعمال اگر بیارزد
xui-split set MAIN --concurrency 8   # قفل دستی ·  --auto برداشتن قفل
xui-split set MAIN --concurrency 0   # قفل روی «بدون mux»
xui-split smart off                  # mux هوشمند برای همه‌ی مسیرها خاموش (on: روشن)
```

**همه‌ی مسیرها:** هر مسیر پشتیبانی که نگهبان ممکن است کاربرها را به آن ببرد هم کپی mux و پورت probe خودش را
می‌گیرد (mux آماده). بعد از failover، نگهبان همان تقسیم مسیر اصلی را روی پشتیبان می‌سازد: سنگین، UDP و تلگرام به خود
مسیر، ترافیک سبک به mux آن (اگر mux گیر کند فقط سبک بدون mux می‌رود). اندازه‌گیری برای پشتیبان‌ها هم انجام می‌شود و
«بدون mux» (۰) هم یکی از گزینه‌هاست؛ فقط وقتی واضحاً بهتر باشد انتخاب می‌شود (در تساوی mux می‌ماند). در صفحه،
کلید «mux هوشمند برای همه‌ی مسیرها» کل اندازه‌گیری را روشن/خاموش می‌کند و هر مسیر «خودکار» یا قفل دستی دارد.

## tunnel-guard - جابجایی خودکار کاربران بین مسیرها

هر دقیقه (تایمر systemd):
- هر مسیر را با یک درخواست HTTPS واقعی از پورت probe خودش می‌سنجد (با یک تلاش دوباره)، به‌علاوه‌ی ping و عمر هندشیک؛
- اگر مسیر اصلی **۲ بار** پشت سر هم جواب ندهد، کاربران (و DoH کش DNS) از راه API مسیریابی Xray به اولین پشتیبان سالم
  می‌روند: **بدون ری‌استارت، بدون قطع کسی**. بعد از **۳ بار** سالم بودن مسیر اصلی برمی‌گردند؛
- هندشیک قدیمی‌تر از ۳ دقیقه ← ری‌استارت `awg-quick@<iface>` (حداکثر هر ۱۰ دقیقه)؛
- هشدار تلگرام (توکن و چت از تنظیمات پنل) از هر مسیری که کار کند، و گزارش روزانه: ترافیک هر تانل، قطعی‌ها،
  پرمصرف‌ترین کاربران، کسانی که تا ۳ روز دیگر تمام می‌شوند یا بالای ۹۰٪ حجم‌اند؛
- ۲۰ روز قبل از تمام شدن گواهی TLS هشدار می‌دهد؛
- مسیر `<name>-mux` را جدا زیر نظر دارد: اگر گیر کند فقط ترافیک سبک از روی mux برداشته می‌شود.

```bash
tunnel-guard --check      # فقط وضعیت
tunnel-guard --test       # پیام آزمایشی تلگرام
tunnel-guard --report     # گزارش روزانه همین حالا
journalctl -t tunnel-guard
```

تنظیمات در `/etc/tunnel-guard.json` است (نمونه: `guard/tunnel-guard.example.json`).
در `backups` **اول همان سرور از راه دیگر** را بگذارید، بعد سرور دیگر؛ تا چیزهایی که به آن خروجی خاص وابسته‌اند قطع نشوند.

## xui-path - مسیر پشتیبان از روی لینک کانفیگ

یک مسیر یعنی سه چیز که باید با هم جور باشند: اوت‌باند در قالب Xray پنل، یک پورت socks محلی برای probe،
و یک ردیف در `/etc/tunnel-guard.json`. این ابزار هر سه را یک‌جا می‌سازد:

```bash
xui-path list
xui-path add TR2 "vless://<uuid>@tr.example.com:443?type=ws&security=tls&path=%2F#TR2"
xui-path add TR2 "vless://..." --addrs 10.0.10.1,10.0.30.1   # آدرس‌های دیگر همان سرور
xui-path remove TR2
xui-path prune       # پورت‌های probe که اوت‌باندشان حذف شده (بدون ری‌استارت)
```

لینک‌های vless، trojan، vmess و shadowsocks (tcp/ws/xhttp/grpc/httpupgrade با none/tls/reality) را می‌فهمد،
و دو پروتکل QUIC (روی UDP) برای پشتیبان سریع روی لینک پر loss:

- `hysteria2://` (یا `hy2://`): در خود Xray؛ دقیقاً همان‌طور ساخته می‌شود که پنل 3x-ui از همان لینک می‌سازد
  (obfs از نوع salamander و پرش پورت `mport` به ماسک‌های finalmask تبدیل می‌شوند).
- `tuic://`: Xray پروتکل TUIC ندارد؛ راه استاندارد sing-box کنار آن است: یک پورت SOCKS محلی در
  `/etc/sing-box/config.json` که sing-box آن را با TUIC می‌فرستد، و اوت‌باند مسیر همان پورت است. sing-box لازم است
  و افزودن یا حذف چنین مسیری sing-box را ری‌استارت می‌کند.

هر دو روی UDP‌اند: جایی که UDP به خارج محدود است کار نمی‌کنند و نگهبان سراغشان نمی‌رود.

کانفیگ را قبل از هر تغییری تست می‌کند، بکاپ می‌گیرد، x-ui را ری‌استارت می‌کند و بعد واقعاً از مسیر جدید وصل می‌شود
تا بگوید جواب می‌دهد یا نه. **بعد از ساخت مسیر، همان کانفیگ روی آدرس همه‌ی تانل‌های هاب امتحان می‌شود** و هر آدرسی
که جواب بدهد زیر همین مسیر ثبت می‌شود (بخش بعد).

## xui-tunnel - یک مسیر، چند تانل به یک سرور

تانل GRE و تانل AWG به یک سرور خارج، همان سرویس Xray را روی دو آدرس می‌دهند (مثلاً `10.0.1.2` و `10.0.10.1`).
پس لازم نیست برای هر تانل یک مسیر جدا بسازید؛ هر مسیر یک فهرست آدرس دارد و اوت‌باندش بین آن‌ها جابجا می‌شود.

```bash
xui-tunnel discover                          # همه‌ی تانل‌ها، مقصد هر کدام، کدام مسیر رویش است
xui-tunnel scan MAIN --save               # کانفیگ MAIN روی آدرس همه‌ی تانل‌ها؛ آن‌هایی که جواب دادند ثبت شوند
xui-tunnel add MAIN 10.0.1.2@sb0        # همان آدرس از داخل تانل sing-box
xui-tunnel add MAIN 10.0.30.1            # یک آدرس دستی (تست می‌شود، حتی اگر هنوز بالا نیامده نگه داشته می‌شود)
xui-tunnel set MAIN 10.0.1.2,10.0.10.1 --auto on   # فهرست به ترتیب ترجیح + جابجایی خودکار
xui-tunnel use MAIN 10.0.10.1            # همین حالا جابجا کن
xui-tunnel list
```

- **discover** تانل‌های کرنل را می‌خواند: برای GRE آدرس remote، برای AWG/WireGuard آدرس endpoint یا مقصد `wss://`
  سرویس wstunnel که آن را حمل می‌کند، و برای تانل sing-box سروری که کانفیگ sing-box به آن می‌رود.
- **تانل sing-box** جور دیگری استفاده می‌شود: آدرس همان می‌ماند و اوت‌باند **از داخل** تانل فرستاده می‌شود.
  ورودی `10.0.1.2@sb0` یعنی `sendThrough` اوت‌باند روی آدرس خود تانل `sb0` تنظیم شود؛ مسیریابی هاب آن را
  به تانل می‌دهد، sing-box تا سرورش می‌برد و اتصال به همان سرویس Xray آنجا می‌رسد
  (اندازه‌گیری: MAIN از `sb0` در ۴۸۶ و BACKUP از `sb1` در ۳۱۴ میلی‌ثانیه). وقتی مسیری روی چنین ورودی است،
  نگهبان زمان رفت‌وبرگشت را از داخل همان تانل می‌سنجد.
- **scan** به حدس مقصد تکیه نمی‌کند: خود اوت‌باند مسیر را برای هر آدرس تانل در یک Xray موقت، همزمان، اجرا می‌کند و
  آن‌هایی که صفحه را باز کنند نگه می‌دارد. پس تانلی که مقصدش معلوم نیست هم پیدا می‌شود. حدود ۳ ثانیه طول می‌کشد.
- **use** اوت‌باند و نسخه‌ی mux آن را از راه API خود Xray عوض می‌کند (`rmo` + `ado`): x-ui ری‌استارت نمی‌شود و فقط
  اتصال‌های تانل قبلی قطع می‌شوند. آدرس در قالب پنل هم ذخیره می‌شود و نگهبان از آن به بعد تانل جدید را می‌سنجد.
- **auto** کاری است که `xui-tunnel.timer` هر دقیقه انجام می‌دهد: مسیرهایی که `--auto on` دارند از پورت probe سنجیده
  می‌شوند؛ دو بار بی‌جواب (به فاصله‌ی ۳ ثانیه) ← رفتن به آدرس سالم بعدی با پیام تلگرام؛ بعد از ۳ بار سالم بودن آدرس
  ترجیحی (و حداقل ۱۰ دقیقه بعد از جابجایی) ← برگشت. هر ساعت هم همه‌ی مسیرها دوباره اسکن می‌شوند و آدرس‌های تازه
  در صفحه پیشنهاد داده می‌شوند.

وضعیت در `/var/lib/tunnel-guard/tunnels.json` و فهرست‌ها زیر `"tunnels"` در `/etc/tunnel-guard.json` نگه داشته می‌شوند.
لاگ تصمیم‌ها: `journalctl -t xui-tunnel`.

### استفاده‌ی همزمان از چند تانل

به‌جای «یک تانل در هر لحظه»، اتصال‌های تازه‌ی کاربران یک مسیر بین دو یا چند تانل همان مسیر پخش می‌شوند، تا ترافیک
همیشه روی یک تانل نباشد. چون همه‌ی تانل‌های یک مسیر به یک سرور می‌رسند، IP خروجی کاربر عوض نمی‌شود.

| روش | رفتار |
|---|---|
| **هوشمند** (پیشنهادی) | همه‌ی تانل‌های سالم با هم کار می‌کنند؛ تانلی که بیش از یک‌سوم پینگ‌هایش از دست برود یا از ۱.۵ ثانیه کندتر شود خودکار کنار می‌رود و بعد از بهبود برمی‌گردد |
| **تصادفی** | هر اتصال تازه به یک تانل تصادفی، به نسبت وزن‌ها |
| **نوبتی** | اتصال‌های تازه به نوبت بین تانل‌ها |

- **اولویت:** ترتیب تانل‌ها همان ترتیب فهرست مسیر است (▲ در صفحه). اولی پشتیبان است: وقتی هیچ تانلی جواب ندهد همه به آن می‌روند.
- **وزن:** ۱× تا ۳×؛ تانلِ ۲× دو برابر اتصال تازه می‌گیرد.
- **سلامت:** observatory خود Xray هر تانل را دقیقه‌ای چند بار پینگ می‌کند و تانل مرده را در هر سه روش کنار می‌گذارد. تایمر هم هر ۵ دقیقه
  هر تانل را تست می‌کند و افتادن یا برگشتن آن را به تلگرام خبر می‌دهد.
- **سنجاق موقت (📌):** کل ترافیک مسیر فقط روی یک تانل، بدون ری‌استارت، تا برداشتن سنجاق یا ری‌استارت بعدی x-ui. برای عیب‌یابی.
- **سهم واقعی:** صفحه برای هر تانل درصد ترافیک یک ساعت اخیر را نشان می‌دهد.

```bash
xui-tunnel mix MAIN on 10.0.1.2,10.0.10.1 --how smart            # GRE + AWG، هوشمند
xui-tunnel mix MAIN on 10.0.1.2,10.0.10.1,10.0.1.2@sb0 --how random --weights 2,1,1
xui-tunnel mix MAIN                                                 # وضعیت
xui-tunnel mix MAIN pin 10.0.10.1      # موقتاً فقط AWG      ·      pin none = برداشتن
xui-tunnel mix MAIN off                                             # برگشت به یک تانل
```

روشن یا عوض کردن ترکیب x-ui را یک بار ری‌استارت می‌کند. قبلش Xray کانفیگ را تست می‌کند، بکاپ گرفته می‌شود و بعدش مسیر
از پورت probe خودش سنجیده می‌شود؛ اگر جواب ندهد همه‌چیز خودکار برمی‌گردد.

**پکت لاست:** هر دقیقه به همه‌ی تانل‌های ترکیب همزمان ۲۵ پینگ (هر ۰.۱ ثانیه) زده و ۶ دقیقه‌ی آخر نگه داشته می‌شود.
تانلی که ۳٪ یا بیشتر لاست داشته باشد و دست‌کم ۲ واحد از تمیزترین تانل بدتر باشد، در حالی که تانل تمیزی می‌ماند، از Xray در حال
اجرا بیرون می‌رود (کپی‌هایش از راه API برداشته می‌شوند؛ بدون ری‌استارت و بدون دست زدن به قالب پنل) و به تلگرام خبر داده می‌شود.
بعد از ۳ دقیقه‌ی تمیز برمی‌گردد. اگر همه‌ی تانل‌ها به یک اندازه لاست داشته باشند چیزی بیرون نمی‌رود، چون مشکل بعد از تانل‌هاست.
اگر تانل اول (پشتیبان) بیرون برود، کپی‌اش به بهترین تانل باقی‌مانده نشانه می‌رود تا پشتیبان همیشه وجود داشته باشد. بعد از
ری‌استارت x-ui وضعیت دوباره اعمال می‌شود. در صفحه کنار هر تانل لاست ۶ دقیقه دیده می‌شود.

**چطور کار می‌کند:** برای هر تانل یک کپی از اوت‌باند مسیر ساخته می‌شود (`mix~MAIN~1`، `mix~MAIN~2`، و برای وزن ۲× یک `mix~MAIN~1b`)،
یک بالانسر `mix-MAIN` بینشان انتخاب می‌کند و قانون‌هایی که به `MAIN` می‌رفتند (کاربرها، DNS، probe نگهبان) به بالانسر می‌روند.
خود `MAIN` بی‌استفاده می‌ماند و الگوی کپی‌هاست؛ پس tunnel-guard (جابجایی بین مسیرها)، xui-split، xui-optimizer و config-guard
بدون تغییر رفتار کار می‌کنند و xui-split بعد از هر ساخت دوباره، ترکیب را هم دوباره اعمال می‌کند. `MAIN-mux` هم همین‌طور
روی همان تانل‌ها پخش می‌شود. config-guard بالانسرها و observatory را هم نگه می‌دارد.
از loopback استفاده نشده، چون Xray ترافیک loopback را دوباره به حساب همان کاربر می‌نویسد و حجم کاربران دو برابر سریع تمام می‌شد.
کد مشترک: `lib/xuimix.py`.

### سرعت آپلود، رتبه‌بندی خودکار و آپلودهای سنگین

**سرعت آپلود هر تانل:** هر ۳۰ دقیقه از هر تانل یک مسیر ۶ مگابایت داده‌ی تصادفی به speed.cloudflare.com فرستاده می‌شود،
از یک Xray موقت جدا (ترافیک هیچ کاربری نیست و در حجم کسی حساب نمی‌شود)، یکی‌یکی تا تانل‌ها خط خروجی هاب را با هم تقسیم نکنند.
تانلی که پینگش جواب نمی‌دهد منتظرش نمی‌ماند. در صفحه، زیر تانل‌های هر مسیر یک نوار جدا «سرعت آپلود تانل‌ها» هست، با پکت لاست،
پایداری و رتبه‌ی هر تانل؛ ⇡ همان لحظه می‌سنجد (`xui-tunnel upload NAME`).

**ترتیب هوشمند:** امتیاز هر تانل = آپلود (میانه‌ی سه اندازه‌گیری آخر) × (۱ − پکت لاست/۲۰٪) × پایداری² (سهم تست‌هایی که جواب
داد). چون تانل فعلی هنگام اندازه‌گیری با کاربرها شریک است، آپلود فعلی کاربرها به آن برگردانده می‌شود. وقتی تانلی سه دقیقه پشت هم
یک‌چهارم بهتر از تانل فعلی بود (و ۳۰ دقیقه از جابجایی قبلی گذشته)، مسیر بدون ری‌استارت رویش می‌رود و به تلگرام خبر داده می‌شود؛
اگر تانل فعلی بمیرد، بهترین تانلی که جواب بدهد انتخاب می‌شود. جابجایی دستی (⇄) یا عوض کردن ترتیب (▲) ترتیب را «دستی» می‌کند
تا دوباره ترتیب هوشمند روشن شود: `xui-tunnel order NAME auto|manual`.

**آپلود سنگین:** هر دقیقه شمارنده‌ی آپلود کاربرها از Xray خوانده می‌شود (فقط خواندن؛ بدون reset، همان شمارنده‌ای که پنل با آن
حجم حساب می‌کند). کاربری که دو دقیقه پشت هم بیش از ۴ مگابیت آپلود کند (`heavy_up_mbps` در `/etc/tunnel-guard.json`)، برای
خودش قانون می‌گیرد، جلوتر از قانون‌های مسیر، به کپی همان مسیر روی بهترین تانل دیگر (`up~NAME`)؛ فقط اتصال‌های تازه‌ی همان کاربر،
تا یک آپلود بزرگ تانلی را که همه رویش‌اند پر نکند و خودش هم تانل خالی بگیرد. ۱۰ دقیقه بعد از آرام شدن قانون‌ها برمی‌دارند.
همه با xuilive و بدون ری‌استارت؛ وقتی نگهبان مسیر اصلی را failover کرده، کاری نمی‌کند. خاموش/روشن: `xui-tunnel steer off|on`.
حجم کاربر عوض نمی‌شود: Xray حجم را روی کاربر می‌شمارد، نه روی اوت‌باند.

## xui-mtu - نگهبان MTU، هر دو سر تانل‌ها

تانلی که MTU آن از توان مسیر بزرگ‌تر باشد ping و بسته‌ی کوچک را رد می‌کند ولی بسته‌ی کامل گم می‌شود (blackhole): صفحه‌ها گیر
می‌کنند و سرعت می‌افتد، در حالی که تانل زنده به نظر می‌رسد. xui-mtu هر ۵ دقیقه (`xui-mtu.timer`) از داخل هر تانل ping با «تکه
نشو» به اندازه‌ی MTU می‌فرستد. اگر رد شد کاری نمی‌کند. اگر نه، بزرگ‌ترین اندازه‌ای را که رد می‌شود پیدا می‌کند (هر اندازه ۴ بار، تا
پکت لاست با مسیر کوچک اشتباه نشود)، سر دیگر را هم در جهت برعکس می‌سنجد، و فقط وقتی دو بار پشت هم همان را دید MTU را در هر دو سر
پایین می‌آورد. پایین آمدن MTU اتصال‌های باز را قطع نمی‌کند (TCP بسته‌های کوچک‌تر می‌فرستد).

- تانلی که ترافیک دارد هیچ‌وقت خودکار بالا نمی‌رود؛ تانل بیکاری که قبلاً پایین آمده هر ۶ ساعت با MTU قبلی امتحان می‌شود.
- تانل داخل تانل بعد از تانل بیرونی سنجیده می‌شود. تانل‌های روی TCP (AWG داخل wstunnel، Backhaul، sing-box) بسته گم نمی‌کنند و دست نمی‌خورند.
- تانلی که نگهبان MTU دیگری دارد (mtu-guard، gre-mtu-guard، mh-mtu-guard در هر کدام از دو سر)، یا MTU آن را چیز دیگری عوض کرده (تا یک روز)،
  دست نمی‌خورد: دو نگهبان روی یک تانل MTU را مدام بالا و پایین می‌برند.
- تغییر در فایل خود تانل (unit سیستمد یا کانفیگ awg/wg) و در `/etc/xui-mtu.pins` نوشته می‌شود؛ cron هر ۵ دقیقه آن را دوباره اعمال
  می‌کند، چون تانلی که از نو ساخته شود با مقدار قدیمی برمی‌گردد.

**سرورهای خارج:** با کلید SSH خود هاب (`/etc/xui-optimizer/ssh/id_ed25519`) وصل می‌شود: اول آدرس عمومی سرور، بعد از داخل تانل‌ها.
چیزی آنجا نصب نمی‌شود؛ `lib/xuiagent.py` در هر بار اجرا فرستاده و با python3 خود سرور اجرا می‌شود. `xui-mtu key` کلید و
دستور گذاشتنش را نشان می‌دهد (در صفحه هم هست)؛ `xui-mtu host ADDR --port N` یک سرور با پورت SSH دیگر را اضافه می‌کند.

**کرنل همه‌ی سرورها:** `xui-mtu kernel` همان سه تنظیم TCP را روی هاب و هر سرور خارجی که در دسترس است می‌سنجد (تایمر هر ۶ ساعت)؛
`--apply` فقط جایی که لازم است اعمال و در `/etc/sysctl.d/99-proxy-tcp.conf` ثبت می‌کند. در چک‌آپ صفحه دکمه‌ی «اعمال و ثبت دائم» هست.

    xui-mtu status | check [--apply] | key | host ADDR | kernel [--apply] | on | off

## xui-reach - دسترسی هاب از داخل ایران

همه‌ی probeهای هاب از خود هاب به بیرون‌اند؛ ولی قطعی کاربر اغلب در مسیر اپراتور او تا هاب است. این ابزار از
نقطه‌های داخل ایرانِ check-host.net (تهران، اصفهان، شیراز، قم؛ هر کدام در یک شبکه‌ی جدا) به هر پورت عمومی هاب
و پورت لینک اشتراک اتصال TCP واقعی می‌زند و نتیجه را ۴۸ ساعت نگه می‌دارد. اگر پورتی دو دور پشت سر هم از بیشتر
نقطه‌ها وصل نشود، و وقتی برگشت، در تلگرام خبر می‌دهد. این نقطه‌ها شبکه‌ی دیتاسنتر هستند، نه خود اپراتورهای موبایل.
آدرس و پورت‌های هاب به check-host.net فرستاده می‌شود.

```bash
xui-reach                        # یک دور: جدول پورت × شهر
xui-reach nodes                  # نقطه‌ها و شبکه‌ی هر کدام
systemctl enable --now xui-reach.timer
```

تنظیم اختیاری در `/etc/xui-reach.json`: `host` (دامنه به‌جای IP)، `ports`، `nodes`، `fails_to_alert`.
در صفحه: کارت «دسترسی از داخل ایران» در تب سلامت.

## xui-geo - فهرست‌های ایران و بستن بدافزار

قانون‌های `ir-direct` به فایل‌های `geosite_IR.dat` و `geoip_IR.dat` (از Chocolate4U/Iran-v2ray-rules) تکیه
دارند، ولی پنل فقط وقتی خودش به‌روز شود آن‌ها را عوض می‌کند؛ روی هابی که مدت‌ها روشن است ماه‌ها قدیمی می‌مانند.

```bash
xui-geo status --latest          # سن فایل‌ها و آخرین نسخه
xui-geo update --restart         # دانلود، بررسی sha256 و آزمایش با Xray، جایگزینی؛ ری‌استارت فقط اگر عوض شد
xui-geo security on|off          # بستن malware، phishing و cryptominers برای همه‌ی اینباندهای کاربران
systemctl enable --now xui-geo.timer   # هفتگی، نیمه‌شب جمعه
```

دانلود اول مستقیم و اگر نشد از پورت‌های probe (از داخل تانل‌ها) است. در صفحه: «فهرست‌های ایران» و کلید «بستن
بدافزار، فیشینگ و استخراج رمزارز» در ابزارها.

## xui-cert - تمدید خودکار گواهی

گواهی‌ای که با `--dns` تنها (دستی) صادر شده خودش تمدید نمی‌شود: cron مربوط به acme.sh اجرا می‌شود ولی رکورد TXT
تازه لازم دارد و می‌ایستد. با API سرویس DNS همان cron رکورد را خودش می‌سازد و پاک می‌کند، فایل‌ها را همان جایی
نصب می‌کند که پنل می‌خواند و x-ui را ری‌استارت می‌کند.

```bash
xui-cert status                                                   # گواهی‌های پنل، اشتراک و nginx
export Arvan_Token="apikey ..."                                   # یک بار؛ acme.sh نگهش می‌دارد
xui-cert auto hub.example.com --dns dns_arvan --test               # فقط آزمایش توکن (staging)
xui-cert auto hub.example.com --dns dns_arvan                     # از این به بعد خودکار
```

برای Cloudflare: `CF_Token` و `--dns dns_cf`. در صفحه، کارت گواهی می‌گوید تمدید خودکار است یا دستی.

## لینک اشتراک (پنل 3.3 به بعد)

مرورگری که لینک اشتراک را باز کند صفحه‌ی اشتراک می‌گیرد (حلقه‌ی مصرف، حجم باقی‌مانده، وارد کردن یک‌لمسی، راست‌به‌چپ
برای فارسی) و اپ‌ها کانفیگ‌ها را. چکاپ صفحه هر دو را با یک کلاینت واقعی امتحان می‌کند، به‌علاوه‌ی روشن بودن
سرویس اشتراک و اعتبار گواهی آن.

## xui-subpage - صفحه‌ی اشتراک فارسی

3x-ui زبان صفحه‌ی اشتراک را جدا از پنل نگه می‌دارد (کوکی `subLang` در مرورگر کاربر) و پیش‌فرضش زبان گوشی است؛
گوشی انگلیسی صفحه را انگلیسی می‌بیند. 3x-ui می‌تواند صفحه را از یک قالب بسازد (تنظیمات ← اشتراک ← Sub Theme
Directory). این ابزار قالب را از **خود صفحه‌ی پنل** می‌سازد (از داخل باینری x-ui برمی‌دارد)، پس ظاهر دقیقاً همان است؛
فقط این‌ها اضافه می‌شود:

- صفحه برای هر مرورگر یک بار فارسی می‌شود؛ دکمه‌ی زبان خود صفحه بعد از آن هم کار می‌کند
- تاریخ‌ها شمسی، وقتی صفحه فارسی است (تقویم خود پنل دست نمی‌خورد)
- اشتراکی که **تاریخش گذشته** یا **حجمش تمام شده** (یا غیرفعال شده) یک مهر قرمز وسط صفحه می‌خورد؛ هر ۳۰ ثانیه تازه می‌شود

```bash
xui-subpage on        # ساختن و روشن کردن؛ یک اشتراک واقعی را امتحان می‌کند و اگر نشد تنظیم قبلی را برمی‌گرداند
xui-subpage status    # کدام صفحه نمایش داده می‌شود و آیا با نسخه‌ی پنل جور است
xui-subpage off       # برگشت به صفحه‌ی دست‌نخورده‌ی پنل
xui-subpage detect    # دیتابیس (SQLite یا PostgreSQL) و باینری پنل که پیدا شده
```

نام فایل‌های اسکریپت صفحه با هر نسخه‌ی پنل عوض می‌شود؛ `xui-subpage.path` با عوض شدن باینری x-ui قالب را خودش
دوباره می‌سازد (`on` روشنش می‌کند). ری‌استارت لازم نیست؛ پنل تنظیم را در هر درخواست می‌خواند.

دیتابیس همان‌طور که خود x-ui می‌بیند تشخیص داده می‌شود: محیط پروسه‌ی در حال اجرا، بعد تنظیمات سرویس
(`/etc/default/x-ui`)، بعد SQLite پیش‌فرض. پنل روی **PostgreSQL** (`XUI_DB_TYPE=postgres`) هم کار می‌کند (`psql` لازم
است). گزینه‌های `on`: `--no-jalali`، `--no-stamp`، `--always` و `--sub LINK` برای امتحان با یک اشتراک مشخص. همین ابزار
جدا هم منتشر شده: [3x-ui-sub-fa](https://github.com/MaxTeller95/3x-ui-sub-fa).

## config-guard - برگشت خودکار قانون‌های مسیریابی

ذخیره کردن یک اینباند از تب پنلی که قبل از آخرین تغییر باز شده بود، باعث می‌شود x-ui قالب قدیمی Xray را بنویسد و
کش DNS، تقسیم ترافیک و قانون‌های دستی بی‌صدا پاک شوند. config-guard از همه‌ی قانون‌های نشان‌دار (ruleTag)،
اوت‌باندهای پروکسی، پورت‌های probe و بخش dns یک مبنا نگه می‌دارد؛ به محض نوشته شدن `config.json` (و هر ۱۰ دقیقه)
بررسی می‌کند و هر چه گم شده باشد را **در جای اصلی‌اش** برمی‌گرداند، تست می‌کند، بکاپ می‌گیرد، x-ui را ری‌استارت
می‌کند و در تلگرام خبر می‌دهد.

```bash
config-guard              # بررسی، بدون تغییر
config-guard --fix        # کاری که systemd اجرا می‌کند
config-guard --save       # قانونی را عمداً حذف کرده‌اید: وضعیت فعلی مبنای جدید شود
```

## xui-probe-client - «مشکل از ماست یا از کاربر؟»

هاب همان کانفیگی را می‌سازد که اپ کاربر از لینک اشتراک می‌گیرد، به پورت عمومی خودش وصل می‌شود و می‌سنجد:

```bash
xui-probe-client alice
```

چیزی در پنل ساخته یا عوض نمی‌شود و UUID چاپ نمی‌شود. در صفحه‌ی Optimizer با کلیک روی نام هر کاربر اجرا می‌شود.

## path-score - این IP ارزش خرید دارد؟

قبل از خرید سرور، از روی هاب اجرا کنید: ۳۰ اتصال TCP واقعی، RTT، و پایداری مسیریابی BGP شبکه در ۳۰ روز گذشته.
چیزی را تغییر نمی‌دهد.

```bash
path-score 198.51.100.50
path-score new.example.com --json
```

## صفحه‌ی Optimizer (پوشه‌ی dash)

یک گزینه‌ی **Optimizer** در منوی سمت چپ پنل (بالای خروج) که صفحه‌ای با تم روشن/تیره‌ی پنل باز می‌کند و روی گوشی هم
کار می‌کند. نوار بالا همیشه دانلود، آپلود، تعداد آنلاین و مسیر فعلی را نشان می‌دهد.

- **نمای کلی:** نمودار ترافیک ۳ یا ۲۴ ساعت با تعداد آنلاین، سهم هر مسیر، سلامت و RTT هر مسیر و دکمه‌ی
  «کاربران اینجا بمانند».
- **کاربران:** چه کسی الان دانلود می‌کند، چه کسی تا یک هفته تمام می‌شود، چه کسی بالای ۸۵٪ حجم است، چه کسی از چند
  آدرس همزمان وصل است و چه کسی یک ماه نیامده؛ به‌علاوه‌ی تست اتصال با کانفیگ هر کاربر، و **سرعت واقعی کاربران به تفکیک
  اینباند**: برای هر کاربر سریع‌ترین آپلود و دانلود ۲۴ ساعت اخیر (میانگین ۵ ثانیه‌ای از آمار Xray)، و میانه و ۹۰٪ آن
  بین کاربران هر اینباند؛ تا دو نوع اتصال (مثلاً WebSocket روی ۸۰ و TLS روی ۴۴۳) روی شبکه‌ی خود کاربران مقایسه شوند.
- **سلامت:** دکمه‌ی **چکاپ** (ساعت سیستم، `xray -test`، **فقط مسیرهای فهرست مسیرها**، سرعت واقعی، کش DNS، MTU تانل،
  منابع، گواهی، دیتابیس پنل، کرنل) با نمره؛ **بازرسی پنل** با دکمه‌ی «تعمیر کن» (از جمله پورت probe بی‌صاحب)؛
  نگهبان پیکربندی؛ مصرف ماهانه‌ی تانل‌ها؛ قطعی‌های اخیر.
- **ابزارها:**
  - **مسیرها:** زنجیره‌ی جابجایی، فرم افزودن با لینک کانفیگ و آدرس‌های اضافه، و دکمه‌ی حذف؛
  - **تانل‌ها:** دکمه‌ی «پیدا کردن تانل‌ها»، و برای هر مسیر: فهرست آدرس‌ها با «تست»، «برو روی این»، «▲» و «حذف»،
    دکمه‌ی «اسکن تانل‌ها»، فیلد آدرس دستی، کلید جابجایی خودکار، پیشنهادهای اسکن و آخرین جابجایی‌ها؛
  - **سرویس‌ها:** وضعیت و دکمه‌ی ری‌استارت x-ui، nginx، نگهبان‌ها و تانل‌ها؛
  - **بکاپ:** گرفتن، دانلود، بازگردانی و پاک‌سازی قدیمی‌ها؛
  - «این آدرس از کدام مسیر باز می‌شود؟»، لاگ‌ها و mux-bench.

فایل باینری پنل دست نمی‌خورد، پس آپدیت پنل صفحه را از بین نمی‌برد: nginx پنل را سرو می‌کند و یک `<script>` برای
افزودن گزینه‌ی منو به صفحه‌هایش اضافه می‌کند. خود صفحه سرویس کوچکی روی 127.0.0.1 است که فقط با ورود معتبر به پنل
جواب می‌دهد؛ رمز جداگانه ندارد.

```bash
sudo bash install.sh                             # پیش‌فرض: x-ui به 127.0.0.1 و nginx روی پورت پنل
sudo bash install.sh --dash 59085                # آزمایشی روی پورت دوم؛ پنل روی پورت خودش هم می‌ماند
```

اگر بعداً پورت، مسیر پایه یا گواهی پنل را عوض کردید، همین دستور را دوباره اجرا کنید.
بعد از `--move` در تنظیمات پنل «Listen IP» را روی 127.0.0.1 نگه دارید.

## migrate - ارتقای پنل 2.x به 3.x

- `migrate/upgrade-2x-to-3x.sh`: پنل 2.x را با حفظ دیتابیس به 3.x ارتقا می‌دهد و قبلش بکاپ می‌گیرد.
  اول ریلیز 3.x را طبق توضیح بالای خود اسکریپت در `/tmp/xui-v3` دانلود و بررسی کنید.
- `migrate/purge-twins`: کلاینت‌های «دوقلو» (دو کانفیگ جدا برای یک نفر با یک اشتراک) را به یک کلاینت واقعی
  با چند اینباند در پنل 3.x تبدیل می‌کند. پیش‌فرض فقط تست است؛ با `apply` اعمال می‌شود.

این دو نصب نمی‌شوند و از خود پوشه‌ی سورس اجرا می‌شوند: `bash /opt/xui-optimizer/migrate/upgrade-2x-to-3x.sh`

## abroad-tune و sysctl

- `abroad-tune` / `abroad-tune apply` روی سرور خارج: خروجی freedom اول IPv4 را امتحان کند (سایت‌هایی مثل
  microsoft.com روی IPv6 گیر می‌کردند).
- `sysctl/99-proxy-tcp.conf`: `tcp_slow_start_after_idle=0`، `tcp_notsent_lowat=16384`، `tcp_mtu_probing=1`؛
  بدون ری‌استارت اعمال می‌شود.

| `/var/lib/tunnel-guard/` | وضعیت نگهبان و تانل‌ها |
| `/etc/xui-optimizer/mtu.json`، `/var/lib/xui-optimizer/mtu.json` | تنظیم و وضعیت نگهبان MTU |
| `/etc/xui-optimizer/ssh/` | کلید SSH هاب برای سرورهای خارج |
| `/etc/xui-mtu.pins`، `/etc/cron.d/xui-mtu` | MTUهای ثبت‌شده (روی هاب و هر سرور خارجی که تنظیم شده) |
| `/var/lib/config-guard/` | مبنا و رویدادهای نگهبان پیکربندی |
| `/opt/xo-dash`، `/var/lib/xo-dash` | صفحه‌ی Optimizer و تاریخچه‌ی ۲۴ ساعته‌ی آن |
| `/root/xui-backup-*` | بکاپ‌هایی که هر ابزار قبل از تغییر می‌گیرد |

## حذف

```bash
sudo bash /opt/xui-optimizer/install.sh --uninstall
```

ابزارها، تایمرها و صفحه حذف می‌شوند و پنل دوباره خودش روی پورتش گوش می‌دهد (Listen IP قبلی برگردانده می‌شود). تغییراتی که در پنل اعمال شده (قانون‌های مسیریابی، کش DNS و ...) در خود پنل
می‌مانند؛ برای برداشتنشان قبل از حذف `xui-optimizer --remove` و `xui-split remove` را اجرا کنید.
